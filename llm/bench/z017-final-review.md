## Strengths

- **Prefix fidelity is real, not asserted.** `b.graph.path(.deployed_prefix, "")` is the DESTDIR-free logical prefix (Configuration.zig:1596-1606: "Unaffected by $DESTDIR"), which is exactly what 0.16's `b.install_prefix` was used for. The prefix string is hashed into the fill_prefix run's manifest (Maker/Step/Run.zig:110-120, `man.hash.addBytes(resolved_arg)` for `.path_directory`), so a second install with a different `--prefix` re-runs fill_prefix instead of reusing a stale `config.c`; the Task 1 reviewer only checked the no-change direction, so this closes the gap. `make_absolute` is a plain `cwd ++ path` join for relative input and the identity for absolute input (Maker/Step/Run.zig `convertPathArg`), so an absolute `--prefix` reaches `config.c` and `moar.pc` byte for byte. The C-escaping order is right: `-Wl,-rpath,"@MOAR_PREFIX@/lib"` is escaped at render time and the token replaced afterwards, and the `UnsafePrefix` guard is what makes that commutation safe.
- **Configure-input registration is complete and the failure modes are the benign ones.** Every configure-time filesystem access in `build.zig` and `build/zig/*.zig` goes through `root_files` or registers itself (`thirdparty.globC`, `version.dependOnGitDescribeInputs`); I grepped for every `openFile|openDir|readFile|access|getenv|runFallible` and found no unregistered read. A registered file that later disappears (the loose branch ref that `git gc`/`pack-refs` folds into `packed-refs`) is a cache *miss*, not an error (Cache.zig `checkDiscoveredPath`: `error.FileNotFound => return .{ .path_deleted = … }`), so the next build reconfigures and re-registers through the parent directory. Registering the same path twice through the same API merges (Cache.zig:762 asserts only on a file/directory kind mismatch), and I could not construct a file-vs-directory conflict from the registered set (`.`, `src/gen`, the stage0 parent, the 3rdparty dirs, `.git` (dir, only when packed-refs is missing), `.git/refs/tags`, `.git/refs/heads` (only when the loose ref is missing) versus the files `VERSION`, `build/sources.list`, `build/config.c.in`, `src/zig/root.zig`, `.git/HEAD`, the loose ref, `packed-refs`). Git never prunes `refs/heads`/`refs/tags` themselves, so the one path that could collide (`.git/refs`) cannot in practice.
- **translate_c wiring is faithful.** `Translator.init` builds `mod` with the same target, optimize and `link_libc` (Translator.zig `initInner`); `addConfigHeader` both adds the header to `mod` and passes `-I <output dir>` to the translator; `defineCMacro(name, null)` emits `-DNAME=1`, which is what the old `-DNAME` meant to clang. The fixup pass was removed on a measured zero, with the output `cmp`-identical, not on assumption.
- **The port edits are mechanical and each one was checked for shape.** All eight `@splat` sites carry the explicit array type and the old length (`@sizeOf(Status)`, 128, 501, 301, 11, 13, 301 u32; 8 bool). `@backingInt` lands on `Op` (`enum(u8)`) and `Section` (auto-tagged enum, still has a backing integer). `Optimize.runtimeSafety` is `.debug, .safe => true` (lang.zig:148-153), the same table `std.debug.runtime_safety` wrapped (debug.zig:253), and reading the tiers' own `builtin.optimize` is what the std's deprecation note recommends. `std.mem.print`/`printSentinel`, `Allocator.print[Sentinel]`, `dupeSentinel`, `find`/`findScalar`/`findScalarLast` are the targets the 0.17 std names in its own "Deprecated in favor of" comments, and the old functions are documented as thin wrappers. `bit_set.Static(n).empty` and `bit_set.Dynamic.initEmpty/deinit(allocator)` are the current constructors (bit_set.zig:77, 405, 731, 811).
- **Process hygiene.** One formatting commit per task, semantic commits with reasoning in the body, both trailers on all 18 commits, `zig fmt --check` clean on the head, an honest Deviations list (eight entries the plan did not foresee, each dated), and the Task 5 flake was re-run rather than waved through.

### Important (Should Fix)

1. **The branch's own deprecated-API policy is not met in the build helpers and `tools/zig`, including a file this branch created.** Global Constraints: "every API the 0.17.0 release notes list as deprecated or renamed is replaced by its new form, even when the old name still compiles". The 0.17 std marks these deprecated (`/usr/lib/zig/std/mem.zig:1283 indexOfScalar`, `:1291 lastIndexOfScalar`, `:1385 indexOfAny`, `:1481 indexOf`, `:1304 indexOfScalarPos`; `std/fmt.zig:624 allocPrint`), and commit 93fc4ab98 itself says the "indexOf family" moves, but only `src/zig` was swept:
   - `build/zig/fill_prefix.zig:17` `std.mem.indexOfAny` (new file), `:18` `std.mem.indexOf`.
   - `build/zig/zigimpl.zig:109` `std.mem.indexOf` (file modified by the branch).
   - `build/zig/sources.zig:60, 86` `std.mem.indexOfScalar` (file modified by the branch).
   - `tools/zig/oplist.zig:36, 44`; `tools/zig/sexpr.zig:71` (`indexOfScalarPos`); `tools/zig/expr_ops.zig:31, 48`; `tools/zig/expr_template_compiler.zig:205, 234, 244, 375, 418` plus `std.fmt.allocPrint` at `132, 200, 224`; `tools/zig/tiler_table_generator.zig:107-135, 168` (`lastIndexOfScalar`), `741` plus `std.fmt.allocPrint` at `160, 191, 347, 413, 534`.
   The plan's Task 3 counted "`std.fmt.allocPrint` (14 sites in 4 files)"; the eight sites left in `tools/zig` are the remainder of that count, so this is a gap against the plan, not only against the policy. Fix: one mechanical commit ("Build helpers and tools on Zig 0.17: std.mem.find family and Allocator.print"), `indexOf→find`, `indexOfAny→findAny`, `indexOfScalar→findScalar`, `indexOfScalarPos→findScalarPos`, `lastIndexOfScalar→findScalarLast`, `std.fmt.allocPrint(gpa, …)→gpa.print(…)`; verify with `zig build unit-test` (every `tools/zig` root is in the unit-test step), `zig build check-jit-tools`, `zig fmt --check`. No behaviour change: the old names are aliases of the new ones.

2. **Undocumented RUNPATH change for a build without `--prefix`.** In 0.16 the default prefix reached `InstallPaths.fromBuild` as an absolute path. In 0.17 the default is `Path{ .root_dir = build_root_directory, .sub_path = "zig-out" }` (Maker.zig:674-677), and `mod.addRPath(b.graph.path(.deployed_lib, ""))` (build/zig/moar.zig:166) is rendered through `resolveLazyPathIndexAbs` (Maker/Step/Compile.zig:1336-1340), which returns the bare sub-path when the root directory has no path string (Maker.zig:3708, `root_dir.path orelse return p.subPathOrDot()`), i.e. when build.zig is in the cwd. So a plain `zig build` or `zig build test` now links a `moar` whose second RUNPATH entry is the cwd-relative `zig-out/lib`, while fill_prefix (with `make_absolute`) bakes the absolute cwd-joined prefix into `nqp::backendconfig`. The binary still loads its sibling library through `$ORIGIN/../lib`, so nothing breaks, but it is a behaviour change the docs do not mention: docs/zig-build.md's 0.17 note covers "a relative one gives a relative RUNPATH entry", not that the *default* is one. Fix (docs, one sentence): "Always pass an absolute `--prefix`; without one, 0.17's default prefix `zig-out` is relative to the build root and the RUNPATH entry `zig-out/lib` is too (config.c still gets the absolute path)". I do not recommend re-adding the 0.16 fatal inside fill_prefix: that would make a bare `zig build` fail where 0.16 succeeded.
